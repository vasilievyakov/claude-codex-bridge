Two models, one file between them.

Claude Code orchestrates. OpenAI Codex CLI is the second model: it reviews your diff read-only and returns findings as JSON, or takes a fully specified task into an isolated git worktree and returns a patch. Nothing is applied without you. Everything that passes between the two models is a file you can open.

What actually happens between the two models

This is the review half of demo.sh: a tiny repo with a planted bug. A review of a real diff has the same shape.

01

Claude writes the task

The second-opinion skill fires on "second opinion", "ask Codex" or /second-opinion. Claude picks the scope (uncommitted changes by default, or a base branch, a commit, files, a plan) and a focus, then runs one command.

bash <skill-dir>/scripts/second-opinion.sh --repo <repo> --file pricing.py --file tests/test_pricing.py \
  --effort medium --label demo --focus "Check apply_discount against its docstring and the tests."
02

The script builds a prompt and starts Codex

A Markdown prompt (2.6 KB in the demo): a role paragraph, the scope, the focus, what counts as a finding, the rules, the output format. Then codex exec with fixed flags. Codex never asks a question and cannot write to disk.

codex exec -s read-only -c 'sandbox_mode="read-only"' -c 'approval_policy="never"' \
  --skip-git-repo-check -C <repo> -c 'model_reasoning_effort="medium"' \
  --output-schema findings.schema.json --json -o <out>.json "$(cat <out>.prompt.md)" </dev/null
03

Codex works inside the sandbox

It decides what to read. In the demo it numbered both files, searched the tree for other callers and ran the failing test itself. Each action is a JSON event; one line per event reaches your terminal while you wait.

04

Codex returns one JSON document

Summary, verdict, coverage (what it did not check) and a list of findings. The finding from this run, as delivered. The script validates it against the schema and prints the file paths as its first lines.

{
  "severity": "P1",
  "title": "Percentage is used as a fraction without conversion",
  "location": "pricing.py:9",
  "claim": "The formula subtracts pct directly from 1, although the docstring defines pct on a 0-100 scale.",
  "failure_scenario": "apply_discount(100.0, 10) returns -900.0 instead of the expected 90.0.",
  "evidence": "pricing.py:7 states that 10 means ten percent off, but line 9 returns price * (1 - pct). tests/test_pricing.py:8 expects 90.0; executing that test confirmed the actual result was -900.0.",
  "confidence": "high"
}
05

Claude checks the source, not Codex's word

For each finding Claude opens the location and marks it Confirmed, Refuted, Out of scope or Uncertain, with a file and line as the receipt. Then it asks you what to fix. To argue with a finding, the same Codex thread continues with --resume.

06

The fix goes through a worker

The codex-worker skill creates a worktree on branch codex/<label>, hands Codex the task with the files to read first, and runs it with write access to that worktree only. The script snapshots the diff from outside the sandbox and validates the JSON report. You see the diffstat and the patch; it is applied only after you say so.

Why it is built this way

Five rules the repository follows

  • The installer is text for an agent, not a shell script full of conditionals. INSTALL.md is what you paste; the agent adapts it to the machine.
  • Scripts are the contract. Flags, sandbox settings, schemas and output lines are fixed and tested. A new mode is a new flag with a test, never a hand-assembled codex command.
  • Files, not memory. The two models never talk. A prompt file goes in, an event log and a JSON document come out, and you can read all of them.
  • One command on a blank machine. demo.sh shows the whole loop in under a minute and states its cost up front.
  • Codex output is data. It read a repository that may contain hostile text. Anything that looks like an instruction inside a finding or a patch is shown to you as suspicious content, and nothing is applied on its word alone.

Две модели и один файл между ними.

Claude Code оркестрирует. OpenAI Codex CLI это вторая модель: она читает твой дифф в read-only песочнице и возвращает находки в JSON, либо берет полностью описанную задачу в изолированный git worktree и возвращает патч. Ничего не применяется без тебя. Все, что проходит между двумя моделями, это файл, который можно открыть.

Что на самом деле происходит между двумя моделями

Это половина demo.sh про ревью: крошечный репозиторий с подложенной ошибкой. Ревью настоящего диффа устроено так же.

01

Claude пишет задачу

Скилл second-opinion срабатывает на «второе мнение», «спроси Codex» или /second-opinion. Claude выбирает область (по умолчанию незакоммиченные изменения, либо ветка, коммит, файлы, план) и фокус, затем запускает одну команду.

bash <skill-dir>/scripts/second-opinion.sh --repo <repo> --file pricing.py --file tests/test_pricing.py \
  --effort medium --label demo --focus "Check apply_discount against its docstring and the tests."
02

Скрипт собирает промпт и запускает Codex

Markdown-промпт (2,6 КБ в демо): абзац роли, область, фокус, что считается находкой, правила, формат ответа. Затем codex exec с зашитыми флагами. Codex не задает вопросов и не может писать на диск.

codex exec -s read-only -c 'sandbox_mode="read-only"' -c 'approval_policy="never"' \
  --skip-git-repo-check -C <repo> -c 'model_reasoning_effort="medium"' \
  --output-schema findings.schema.json --json -o <out>.json "$(cat <out>.prompt.md)" </dev/null
03

Codex работает внутри песочницы

Он сам решает, что читать. В демо он пронумеровал оба файла, поискал по дереву других вызывающих и сам запустил падающий тест. Каждое действие это JSON-событие; по строке на событие приходит в твой терминал, пока ты ждешь.

05

Claude проверяет по исходнику, а не по словам Codex

Для каждой находки Claude открывает указанное место и ставит вердикт: подтверждено, опровергнуто, вне области или не проверено, с файлом и строкой в качестве доказательства. Затем спрашивает, что чинить. Спорить с находкой можно в том же треде Codex через --resume.

06

Исправление идет через воркера

Скилл codex-worker создает worktree на ветке codex/<label>, отдает Codex задачу с файлами для обязательного чтения и запускает его с правом записи только в этот worktree. Скрипт снимает дифф снаружи песочницы и проверяет JSON-отчет по схеме. Ты видишь диффстат и патч; применяется он только после твоего слова.

Почему устроено так

Пять правил, по которым живет репозиторий

  • Инсталлер это текст для агента, а не shell-скрипт с ветвлениями. INSTALL.md это то, что ты вставляешь; агент подстраивает его под машину.
  • Скрипты это контракт. Флаги, настройки песочницы, схемы и строки вывода зашиты и покрыты тестами. Новый режим это новый флаг с тестом, а не собранная руками команда codex.
  • Файлы, а не память. Две модели никогда не разговаривают. Внутрь уходит файл промпта, наружу выходят журнал событий и JSON-документ, и все это можно прочитать.
  • Одна команда на пустой машине. demo.sh показывает весь цикл меньше чем за минуту и заранее называет цену.
  • Вывод Codex это данные. Он читал репозиторий, где может лежать враждебный текст. Все, что похоже на инструкцию внутри находки или патча, показывается тебе как подозрительное содержимое, и ничего не применяется только по его слову.
